# 2단계: Legacy FE vs 현재 FE 차이 분석 + 정상 동작 필수 추가사항

## 1. 비교 범위
- 대상 A: 현재 FE (`src/app` 중심, 최신 디자인/기획 반영 버전)
- 대상 B: 레거시 FE (`_legacy/Project_Prometheus_FE/src`)
- 목적: 현재 FE를 실제 서비스로 동작시키기 위해 필요한 기능/레이어 보강 항목 정의

## 2. 아키텍처 차이 요약

| 구분 | 현재 FE | Legacy FE |
|---|---|---|
| 라우팅 | 단순 페이지 라우팅 | 로그인/회원가입/약관/온보딩/보호 라우트 포함 |
| 인증 | 하드코딩 사용자 `AuthContext` | JWT 기반 로그인 + 세션 복원 + 만료 처리 |
| API 계층 | 없음 | `src/api`(endpoint 상수, 에러 표준화, 토큰 주입) |
| 데이터 소스 | `mockData.ts` 중심 | 백엔드 API 실호출 중심 |
| 회사/테넌트 | UI 내부 상태 | `CompanyContext` + company API 연동 |
| 운영 기능 | 시뮬레이션(alert) 다수 | OCR, 업로드, 팩스, 고객센터, 지오펜스, 멤버관리 등 실연동 |

## 3. 기능 차이 상세

### 3.1 레거시에 있고 현재에 없는 핵심 레이어
- 인증 플로우 전반: `Login`, `SignUp`, `ForgotPassword`, `RequireAuth`, `ForcePasswordChange`
- API 클라이언트 계층: 공통 에러 핸들링, 토큰 주입, 응답 표준화
- 회사 컨텍스트: 회사 정보 조회/수정, 로고/문서 업로드 반영
- 멤버 관리: 승인/거절/권한 변경/탈퇴/복원

### 3.2 레거시 실연동 기능 vs 현재 시뮬레이션 기능
- OCR 연동: 레거시는 `ocrExtract` 호출, 현재는 `setTimeout` 기반 더미 처리
- 파일 업로드: 레거시는 업로드 서명/세션 기반, 현재는 로컬 파일 상태만 유지
- 단말 장착 신청: 레거시는 `/terminal-requests` 연동, 현재는 안내 alert
- 고객센터 문의: 레거시는 `/support/tickets` 연동, 현재는 페이지 자체 없음
- 메모 히스토리: 레거시는 API 조회, 현재는 로컬 메모 추가 수준

### 3.3 데이터 모델/도메인 규칙 차이
- 자산/예약 식별자 및 필드명 차이:
  - 현재 FE: `vehicleNumber`, `status(대여중/예약/가용/정비중)` 중심
  - 레거시 FE/BE: `vin`, `plate`, `managementStage`, `contractStatus` 중심
- 계약 상태 체계 차이:
  - 현재 FE: 예약/대여/반납 타입 + UI 규칙
  - 레거시: 상태머신 기반(문의~종결) 전환 API
- 결제/미납 모델 차이:
  - 현재 FE는 `mockPayments`를 별도 사용
  - 레거시는 계약(`rental`) 필드 기반 요약 계산 위주

## 4. 현재 FE 정상 동작을 위한 필수 추가사항

## 4.1 P0 (선행 필수)
- [ ] `src/api` 또는 `src/services` 계층 신설
- [ ] 인증/세션 구조 도입 (로그인, 토큰 저장, `me` 조회, 만료 처리)
- [ ] 페이지별 mock 제거 및 서버 데이터 패치 경로 확보
- [ ] 도메인 타입 재정의(현재 UI 타입 ↔ BE 타입 매핑)
- [ ] 전역 에러/로딩 상태 처리 표준화

## 4.2 P1 (정상 운영 필수)
- [ ] 자산 CRUD + 상세(보험/장치/진단/히스토리) 실연동
- [ ] 예약/계약 생성/수정/반납/취소 실연동
- [ ] 조치 필요 항목 조회/상태 변경/메모 저장 API 연동
- [ ] 결제 상태 및 미납 계산의 서버 기준화
- [ ] 매출 요약(주/월/연) 서버 집계 연동
- [ ] 설정(회사/지오펜스/계정) 서버 연동

## 4.3 P2 (기능 확장/완성도)
- [ ] OCR 자동 추출 실연동(차량등록증/계약서/면허증)
- [ ] 단말 장착 신청 및 장착 작업 연동
- [ ] 고객센터 문의 접수/추적 연동
- [ ] 메모 히스토리/알림센터 고도화

## 5. 권장 구현 방향 (현재 FE 기준)

### 5.1 "도메인 어댑터" 방식 채택
- 레거시 BE 원본 스키마를 FE 컴포넌트에 직접 노출하지 말고 어댑터 계층에서 변환.
- 예시:
  - `plate + vin -> vehicleNumber`
  - `contractStatus -> reservation.type/viewFilter`

### 5.2 점진 전환 순서
1. 읽기 API 우선 연결(대시보드/자산/예약 목록)
2. 쓰기 API 연결(등록/수정/상태변경)
3. 부가 기능(OCR/문의/장착/히스토리) 연결

### 5.3 레거시 기능의 선택적 이식
- 현재 기획에서 화면이 없는 기능(예: 레거시 상세 페이지)은 그대로 이식하지 않고, 도메인 로직/API만 재사용.

## 6. Step 2 완료 기준 (DoD)
- 현재 FE 기준 필수 기능 목록(P0/P1/P2)이 확정된다.
- 레거시 재사용 가능한 자산(API/비즈니스 로직)과 신규 구현 항목이 분리된다.
- 이후 3단계(BE 개발 계획)에서 바로 개발 티켓으로 분해 가능한 수준의 차이 분석이 완료된다.
